# T15.4 interactive service control

Implementation and local regression checks are complete. Live Windows OpenSSH
to Ubuntu acceptance remains **awaiting manual verification**.

## Cause and evidence

The actual menu calls `$result = Invoke-RemoteServiceAction ...`. That captures
the function's success stream, including the stdout of its former `& ssh`
invocation. Under `ssh -tt`, remote stdout and stderr share the PTY, so sudo's
password prompt arrives on SSH stdout. Capturing it hides the prompt (often
without a newline) while SSH waits for the user's password. The later debug
statement and `$LASTEXITCODE` are never reached during that wait. The working
direct SSH command does not have this output capture.

A real native executable probe under Windows PowerShell 5.1 in a console
confirmed `stdin=False stdout=False` for direct invocation versus
`stdin=False stdout=True` under function result assignment (`False` means
unredirected). Piping through `Out-Host` or `Out-Default` still redirected native
stdout. A no-newline native prompt now reaches the console even with assignment.
This confirms the capture defect locally; the reported live SSH hang itself has
not been reproduced here.

The old `printf ... | base64 -d | bash -s` transport completed in local Bash;
that pattern alone did not reproduce a hang. It is not established as the
cause. The replacement decodes into a shell variable, then uses
`exec bash -c "$script" -- service action` only if decoding succeeds.
Code travels in an argument and stdin remains available. A Bash fixture
executes the exact command received by a Windows argv probe and verifies that
an invoked command can read supplied stdin.

## Changes

- `src/SSH/Remote/Invoke-RemoteServiceAction.ps1`: use `Start-Process
  -NoNewWindow -Wait -PassThru` to preserve inherited console handles despite
  result assignment. This is the demonstrated need for Start-Process; simply
  changing Bash transport does not fix captured prompts. Quote the entire remote
  command for Windows argv because PowerShell 5.1 joins `ArgumentList` strings.
  Read `Process.ExitCode` immediately; Start-Process does not set LASTEXITCODE.
- Keep alias-based SSH configuration and identity selection, force interactive
  authentication with `BatchMode=no`, and retain configured host-key verification.
  No agent, password storage, password argument, or sudoers change is required.
- Check systemd, unit existence and `sudo -l -- systemctl action service`
  authorization. Execute only the validated action and service. Preserve SSH
  daemon blocking; tighten full-string input validation against newlines.
- Remote exit codes: 20 = inspection/prerequisite failure, 21 = missing service,
  22 = sudo authentication/permission failure during authorization, 23 = action
  failure, 24 = successful action with failed status retrieval. SSH 255 uses
  common authentication diagnostics to distinguish rejected
  credentials from other SSH connection/configuration failures. Raw SSH stderr
  is held in a temporary file and deleted in `finally`; it is not printed or
  logged. Passwords and passphrases are handled by SSH/sudo's terminal prompts.
- Retrieve updated status with an unprivileged `systemctl show` immediately
  after the action in the same SSH session. Display the properties directly in
  the console, preserving interactive terminal handling without another login.
  There is no `Get-RemoteServiceStatus` call after an action. The returned object
  contains the action summary and `StatusVerified`; active/substate values are
  displayed by the remote command rather than returned as object properties.
  `ExitCode=0` indicates action and status success. `ExitCode=24` returns
  `Success=True`, `StatusVerified=False` and a separate `VerificationError`.
- `devops.ps1`: display the exit code and verification flag, and report failed
  verification as a warning after action success. Existing `-ne 'YES'` already
  accepts all YES letter cases and rejects other values; it stays unchanged.
- `tests/SSH/Remote/RemoteServiceAction.Tests.ps1`: native process/argv/console
  probe, Bash fixtures, validation, error handling, and menu regression checks.

T14, SSH architecture/configuration, and the existing status function are unchanged.

## Manual Windows/Ubuntu acceptance

On a disposable Ubuntu test server, create a dedicated test unit (skip creation
if the existing `devops-demo.service` already serves this purpose):

```bash
sudo tee /etc/systemd/system/devops-demo.service >/dev/null <<'UNIT'
[Unit]
Description=DevOps CLI interactive control test
[Service]
ExecStart=/usr/bin/sleep infinity
[Install]
WantedBy=multi-user.target
UNIT
sudo systemctl daemon-reload
systemctl show devops-demo.service --property=LoadState,ActiveState,SubState
```

Use an ordinary sudo account and a configured, passphrase-protected SSH identity.
Ensure the test key is not already loaded in an agent; the implementation does
not require starting or stopping any agent. In a Windows PowerShell 5.1 console:

```powershell
# Baseline reported working by the project owner.
ssh -tt ubuntu-dev "sudo systemctl stop devops-demo.service"

. ./devops.ps1
foreach ($action in @('Start', 'Stop', 'Restart')) {
    # Clear the remote sudo timestamp to require authentication again.
    ssh -tt ubuntu-dev 'sudo -k'
    $result = Invoke-RemoteServiceAction -HostAlias ubuntu-dev -ServiceName devops-demo -Action $action
    $result | Format-List
}

# Then test the actual menu, including all YES cases and cancellation.
./devops.ps1
```

For each action, verify both the SSH passphrase prompt and sudo password prompt
are visible and usable, SSH returns control, `Success=True`, `ExitCode=0`, and
the status matches the operation. An already authenticated sudo session may not
prompt; SSH may use cached credentials if an agent or connection sharing is
configured. Status retrieval must not request another SSH or sudo password;
it uses the original connection and does not invoke sudo. The action's sudo
authorization check and execution still follow the server's sudo policy.

Also manually check:

1. Menu: Start/Stop/Restart accept `YES`, `yes`, `Yes`, `yEs`; empty input, `Y`
   and `no` cancel without SSH. `ssh`/`sshd` control and shell punctuation fail.
2. A nonexistent unit reports service-not-found. A harmless failing test unit
   reports action failure without claiming success.
3. Rejected SSH credentials report authentication failure; an unreachable test
   alias or untrusted/changed host key reports connection failure. Do not bypass
   host-key verification to make these tests pass.
4. Incorrect sudo credentials or denied command privileges report sudo failure.
   Use a disposable account rather than altering broad sudo rules.
5. If status retrieval is deliberately made unavailable after a successful
   action, the menu reports completed action plus a verification warning and
   SSH exit 24. Local Bash and native exit-code fixtures cover this boundary.
6. Recheck SSH connection, read-only status/listing and T14 from their menus.

On Ubuntu, independently inspect the unit after each operation:

```bash
systemctl show devops-demo.service --property=LoadState,ActiveState,SubState
sudo journalctl -u devops-demo.service -n 20 --no-pager
```

Only if this test created the disposable unit, remove it afterward:

```bash
sudo systemctl stop devops-demo.service
sudo rm -- /etc/systemd/system/devops-demo.service
sudo systemctl daemon-reload
```

## Remaining limits

- Live interactive SSH/sudo acceptance has not been executed here.
- SSH authentication classification recognizes common English OpenSSH messages;
  other exit-255 diagnostics fall back to connection failure. A disconnect after
  submission leaves the action outcome uncertain; check status before retrying.
- sudo and systemctl can both return 1. The separate authorization check makes
  normal authentication/permission failure distinct, but a changed policy,
  expired credentials, or authentication failure between check and execution
  can still produce action exit 23. Its message explicitly includes this case.
- Updated status is console output, while the returned object contains the
  action summary and verification result. Use the unchanged standalone
  `Get-RemoteServiceStatus` when structured status properties are needed; that
  explicit call opens its own connection.
- Waiting for the user's input or a real systemd job is intentional; this fix
  does not add an arbitrary timeout to interactive input or service operations.
- Diagnostic temporary files use the Windows user's normal temporary directory.
  No credentials are supplied to or logged by the CLI; forcibly terminating
  PowerShell can prevent normal temporary-file cleanup.
- The repository's historical full-suite discovery problems are outside this
  fix. Isolated suite results must not be presented as a green whole-repo run.
